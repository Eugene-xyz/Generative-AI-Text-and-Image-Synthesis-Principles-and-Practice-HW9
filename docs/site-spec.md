## 首頁內容順序

1. 導覽與主視覺：名稱、副標、樂團導讀、成員與歌曲入口、合照位置。
2. 成員：CHODAN、MAGENTA、HINA、SIYEON，摘要取自各自的 Wiki，導向可閱讀的詳細資料。
3. 三首推薦：依 `featured_order` 顯示 Dear、T.B.H、Dreamer；取用推薦理由、版本、官方入口，不另抄網址。
4. 作品旅程：以既有正式發行日期排序，首頁精選入口，詳細目錄保留分類與收錄範圍。
5. 時間線：精選既有已完成事件；出道、演出、頒獎典禮與音樂節目一位的類別保留。發行日期仍引用作品。
6. 來源與關於：非官方性質、資料截止範圍、來源入口及後續照片署名。

## 內容載入與呈現

- `wiki/` 與 `raw/sources/` 保留原位置；Astro 於建置時載入，人工事實只在 Wiki 維護。首頁選取 ID 的設定不是第二份內容資料庫。
- 草稿預覽與公開輸出分離。預覽可讀 `draft`／`partial`，必須 noindex；公開建置需檢查 ready、無 conflict、逐頁發布審閱與檔案雜湊。partial 保留已確認的具體限制及審閱紀錄，不升格成 checked；規則見 AGENTS 第 6 節。
- 成員使用正式職涯版型，作品／影音使用正式音樂版型；時間線與事件採共用正式版型，樂團及推薦使用共用正式版型，保留來源與必要待查資訊。不要為了導覽而產生空白頁或假連結。
- 呈現 Markdown 時排除 YAML 編輯欄位與內部版本 ID 區段，保留讀者需要的版本、日期限制及來源。內部相對連結統一轉成網站路徑，對於不對外呈現的管理文件提供可理解的替代入口。
- HTML 輸出需處理外部內容安全，不執行來源中的程式或任意 HTML 指令。未知來源與未支援的內部連結要在檢查時被發現。

## 共用版型與響應式

目前實作首頁 `/`、成員總覽 `/members/`、四位成員 `/members/<slug>/`、全部筆記 `/library/`、通用閱讀 `/read/<原 Wiki 資料夾>/<檔名>/`，以及 `/sources/`。本輪另有音樂總覽 `/discography/`、曲目索引 `/discography/tracks/`、13 個 `/discography/<slug>/`、7 個 `/collaborations/<slug>/` 及 1 個 `/other-songs/<slug>/`。舊音樂 `/read/` 路由共用 `MusicWork.astro`，新連結統一導向正式音樂路由。舊 `/read/members/<slug>/` 保留並套用同一份成員版型；全站新連結經 `entryUrl()` 指向正式成員路由，不維護兩套人物頁。

### 成員頁的共用呈現

- `MemberProfile.astro` 負責四頁共用版型：姓名與照片 → 成員切換 → 組團前經歷 → 加入 QWER → 角色 → 職涯年表 → 資料限制 → 來源與下一位成員。
- `src/lib/members.ts` 由既有章節提取內容，年表使用 Markdown parser 讀取「時間／內容／日期的意義」三欄。僅重排顯示，不把報導日轉成首次活動日、不自行排序推定未知先後。
- 必須保留「組團前做什麼」「如何走向 QWER」「樂團中的角色」「已能確認的時間節點」「下一輪待查」標題；「時間資訊的限制」可選。未知新章節會使建置報錯，避免新增內容後悄悄漏呈現。若要改結構，同步更新模板及轉換。
- 開場藝名與資料範圍放在「藝名與介紹範圍」可展開區；不丟棄 Siyeon 的 NMB48 原名來源。內文外部引用、本人回憶歸屬、不同報導的表述差異與具體待查事項保留。
- 編輯流程句（例如「使用者確認寫法不代表公開」）不在人物正文展示；全站預覽狀態由頁尾與 noindex 說明。Wiki 原文不因此被覆寫。
- 桌面個人照片最寬 440px，保持原比例；總覽桌面四欄、較窄兩欄，照片區以 contain 補齊比例而非裁圖。手機個人頁上下堆疊，左側章節目錄改為兩欄入口，年表改單欄。
- `src/data/member-photos.ts` 只保存使用者已選的素材與署名資料，不保存人物職涯。圖片元件共用，個人頁、總覽與來源頁使用同一筆資料。若未選定照片，僅在本機保留清楚待選提示，不能冒稱已採用。
- Header「四位成員」進入總覽；首頁四個故事入口及 Wiki 回連直接進入個人頁。成員切換以 `aria-current` 標示當前人物；頁內目錄、下一位及返回總覽均為原生連結。

### Wiki 與網站的對應約定

- `src/content.config.ts` 載入 66 個既有實體與來源紀錄；依穩定 `id` 建立關聯。管理文件不直接變成公開文章。
- 成員卡名稱取文章的第一級標題；組團前身分取「組團前做什麼」下第一個第三級標題；角色取「樂團中的角色」段落。沿用模板標題，改標題須同步更新 `src/lib/wiki.ts` 並檢查所有四張卡。
- 推薦卡取「推薦理由（網站導聆）」、表格的「推薦版本」列，以及 frontmatter 的 `listen_url`／`listen_locator`；首頁三首必須與 `featured_order` 一致。
- 正式發行日期取 `release_date`；發行事件用 `release_id` 取得同一日期，不手寫第二份。作品類型取「發行類型」表格列。
- `src/data/home.ts` 只決定顯示哪些 ID 與順序。缺少 ID、必要標題或版本欄時讓建置失敗，禁止靜默猜測或漏掉內容。
- 原始 Markdown 的來源連結保留；編輯用版本對照、選曲查核紀錄及原始 `src-` 編號行不直接呈現，改以完整來源標題閱讀。
- 根目錄正式網站從 dist 匯出為相對路徑及內嵌互動程式，透過 .site-files.json 管理；原始碼與 Wiki 才是人工主檔。歷史 review/ 只屬於早期預覽，交付包不包含它。

主背景和區塊採深色，莓紅用於主要行動、冰藍用於閱讀連結。使用少量分隔線與開放排版；長文有舒適行距與行寬。桌面主視覺雙欄、手機單欄；成員 4／2 欄，歌曲及時間線窄畫面單欄。圖片選定後記錄比例、對焦位置與替代文字，避免裁去成員。

## 互動與可用性

選單、跳到主要內容、錨點、詳細閱讀及官方收聽均須可操作；按鍵焦點可見，不用 hover 作為唯一操作。手機選單要能開關並回報展開狀態。動態尊重減少動態偏好，不自動播放音樂。

## 驗證與後續擴充

依 README 指令做內容關聯、型別與建置檢查，再實際檢視桌面／手機與主要互動。新增資料時依模板與原規則查核；新增同類頁面沿用元件，列表從資料產生。正式部署前測試 GitHub Pages 子路徑與公開狀態篩選。

技術依據：[Astro 內容集合](https://docs.astro.build/en/guides/content-collections/)、[GitHub Pages 部署](https://docs.astro.build/en/guides/deploy/github/)。

## 音樂作品與曲目索引

- `src/lib/music.ts` 使用 Markdown parser 讀取既有表格，分離 H2／H3 章節；`MusicWork.astro` 共用 13 個發行與 8 個影音頁。未知章節、欄名、曲目／簡介／版本對照數量不一致、重複錨點會使建置失敗。不能以「略過」掩蓋缺漏。
- 正式發行依 `release_date` 遞增；影音依 `published_date`，無則用 `reference_date`，顯示 `date_basis`，不替未知公開日補值。不同分類不合併計數。
- 發行頁順序：名稱／日期／簡介及平台封面 → 基本資料 → 背景 → 曲目表 → 逐曲筆記與入口 → 版本限制 → 延伸推薦 → 來源與前後作品。
- 正式發行的錨點由編輯用表格的 `track-` 或 `appearance-` ID 產生 `version-<版本ID>`；正文不展示識別碼。對照與簡介必須依曲目列一致，曲名不符報錯。LP 的「待查」不能轉成數字。
- 影音表每列按「性質」產生穩定錨點（保留 Unicode 字母與數字，其餘轉連字號），同頁不可重複；修改性質名稱時應檢查既有深層連結。不要用列序作錨點。逐版本介紹及入口的限制保留。
- 全部曲目索引由同一資料自動產生：正式發行 48 筆收錄項（數位 41、CD 限定 1、LP 6），另有 11 筆合作影音入口與 1 筆其他公開歌曲入口。60 筆是索引項，不是 60 首不同歌曲或錄音。新增資料後計數自動更新。
- 搜尋只在本頁篩選曲名、作品與版本關鍵字；支援空白分詞、清除、無結果與螢幕閱讀器狀態。關閉 JavaScript 時仍有完整原生連結索引。
- 相同 `song-` 的不同收錄提供折疊連結，不能因此宣稱同一母帶。首張 CD Only、日文／韓文、混音／伴奏、LP 與再收錄限制都保留。
- 封面與播放器的查核記錄見 [素材紀錄](assets.md)。播放器寬度 100%、高 352px；按鈕點擊後才載入，未點擊沒有 iframe 或遠端封面。外開備援始終可用。本站不使用 Apple Music 播放器；原 Wiki 引用的 Apple Music 資料來源不抹除。
- 共用樣式在 `src/styles/music.css`。桌面依年份排列、文章有側邊目錄；窄畫面改為單欄，曲序與待查標記仍可見。`review/` 重新產生後須檢查搜尋及播放器腳本，不能只驗證選單。

## 發展時間線與事件內頁

- `/timeline/` 整合 28 個事件（出道 1、發行 13、演出 7、頒獎典禮 6、音樂節目一位 1），加上 8 個影音主節點與已選的 Shine All Night 日本公開版確認節點，共 37 筆。這是時間節點數，不是不同作品、演出場次或獎座總數。
- 事件新路由 `/timeline/<slug>/` 與舊 `/read/timeline/<slug>/` 共用 `EventPage.astro`；全部 Wiki 回連、首頁與主導覽接到正式路由。影音節點使用已完成的音樂頁，不另建事件實體。
- `src/lib/timeline.ts` 組合 Wiki，正式發行日期與精度只從 `release_id` 對應作品取得；一般事件用本身日期、結束日及 `date_basis`。同日按穩定 ID 顯示，但明示此列序不代表已知先後。
- 類別用文字、英文短標與顏色輔助辨識，不能只用色彩。時間線提供年份及單一類別組合篩選、清除、無結果訊息及即時狀態；JavaScript 不可用時仍可讀完整內容，篩選控制不顯示。
- 精確日期在各年內按日期／期間起日排列；僅年／月的日期放在該年「日期尚未完整確認」區，完全未知另列「日期待查」。不造 1 月 1 日等占位日，也不讓頁面排序暗示未證實的先後。
- 主影音日期沿用公開日或參考日，原 `date_basis` 可見。`src/data/timeline.ts` 只保存已選的追加節點之作品 ID 與版本性質，不抄日期；從 Wiki 版本表讀取字面日期。只支援明確日期或「截至 YYYY-MM-DD 已公開」等可判讀格式，未知格式報錯，不能從新聞 URL 或段落抽出日期。
- Shine All Night 日本公開版沿用原版本段落的來源及演唱語言待查。ANIMA POWER 訪談日、未知 MV 日等沒有自動變成新增時間節點；新增選項先討論。
- 每列有原文摘要及就近引用，另提供來源展開清單，完整來源名稱、查閱日與查核範圍可讀。來源仍取自 Wiki 的 source ID，沒有新增或覆寫 raw 紀錄。
- 14 筆重要活動正文按「事件資料 → 事件內容 → 日期辨識 → 編輯收錄理由 → 範圍與待查 → 來源」呈現。事件資料轉成定義清單，獎項、舞台及日期表格轉成保留原欄名的逐筆記錄，手機不用擠四欄表格。
- H2 必須是 `事件資料`、`事件內容`、`日期辨識`、`收錄理由`、`範圍與待查`、`相關頁面`；缺少或未知章節報錯。出道／發行的既有簡短格式保留原段落，發行事件附作品入口，不複製曲目表或補寫新事實。
- 共用樣式在 `src/styles/timeline.css`；桌面左側年份、日期與右側事件脈絡，手機改垂直排列。正式內頁有日期面板、章節導覽、相關筆記及前後節點。
- 本輪資料仍截止 2026-11-09，實作日期為 2026-11-10。資料查核日不因完成版型改動；本輪發布審閱及 ready 狀態依 AGENTS 第 6 節另行記錄。

- BandPage 依樂團模板的五個 H2 呈現。組團背景沿用既有本人訪談與人物資料，不補猜測日期；合照沿用已選素材，個人故事連回成員頁。

- Spotify 使用既有同版專輯展示設定的外開入口，標明曲目位置；官方影片使用 Wiki 入口。原 Genie、Melon、Apple Music 等查核連結仍在版本表與來源，不作另一套資料庫。
- 共用樣式為 editorial.css；桌面三欄推薦卡，手機單欄，事件／歌曲的長表改為定義清單。所有新導覽指向正式路由，舊 read 路由共用元件。

## 根目錄發布版

- Markdown 章節與表格轉換須統一 LF／CRLF，原文定位失敗時停止建置；跨平台存檔不能使表格內容重複或截斷。
- build:site 強制以根路徑建置，再將站內 href／src 及 CSS 資源轉成相對檔案路徑。這使 Repository 名稱可變更，且不需伺服器也能開啟 HTML。
- 各個獨立互動腳本內嵌並隔離作用域；出現未支援的 import／export 時停止匯出，不能默默輸出失效腳本。
- 生成檔限明確的網站路徑；更新前核對上次雜湊，拒絕手改生成檔或覆蓋非管理檔案。原始碼、Wiki、docs 不在自動移除範圍。
- .gitattributes 保留檔案位元組，避免不同作業系統自動換行破壞發布審閱雜湊。
- GitHub Pages 採 main／根目錄，保留 .nojekyll；原始碼與生成檔一起上傳，node_modules、快取、舊 review 與打包副本不提交。
